Event Notification vs Event-Carried State Transfer

Deux styles de conception pour un même Event Message : que doit contenir l'événement publié sur le topic, et qui a la responsabilité de récupérer l'état complet ? Ce choix traverse la plupart des patterns basés sur des flux Kafka de ce catalogue, notamment le Publish-Subscribe Channel.

Event Notification

L'événement dit qu'un fait s'est produit — pas ce qui a changé. Le consommateur rappelle la source pour obtenir le détail.

Event-Carried State Transfer

L'événement transporte l'état complet dont le consommateur a besoin. Aucun rappel à la source n'est nécessaire.

Comparaison

Critère Event Notification Event-Carried State Transfer
Taille du payload Minimal — id + type d'événement Complet — tout l'état pertinent
Couplage Fort à l'exécution (rappel API requis) Faible — aucune dépendance à l'exécution
Résilience Dépend de la disponibilité de la source Le consommateur reste opérationnel seul
Risque principal Trafic « chatty », latence de rappel Duplication et désynchronisation des données
Cas d'usage typique Notification UI, invalidation de cache Vues matérialisées, CQRS, réplication de données
Choisir Event Notification quand…

Le consommateur n'a besoin de l'information que rarement, ou seulement en réaction à une action utilisateur ; la source expose déjà une API fiable ; on veut éviter de dupliquer des données sensibles.

Choisir ECST quand…

Le consommateur doit rester autonome même si la source est indisponible ; on construit une vue matérialisée, un cache local ou une réplication de données (CQRS).

Concept issu des travaux de Martin Fowler sur les architectures événementielles.
